# PBKDF2 本地钱包升级

本地 keyring 使用 PBKDF2-SHA256、256-bit 密钥和 AES-256-CBC。新钱包使用
600,000 次。旧钱包在启动后首次成功解锁时安排升级。

## 写入策略

`RNEncryptor` 的普通 `encrypt` 仍默认使用 5,000 次，因此预生成助记词、云备份、
keychain 包装数据及其他 `appEncryptorApi` 调用不因本功能改变。显式传入
`keyDerivationOptions` 的调用仍可使用 600,000 次。

keyring 的密码校验密文 `booted` 和 vault 通过 `encryptKeyringState` 写入：

- 当当前 Store 中既没有 vault 也没有 `booted` 时，视为新的本地钱包，使用
  600,000 次。全新创建和向空 App 导入助记词都属于这种情况。
- 普通保存和改密时，vault 与 `booted` 分别继承自身参数。其中一种缺失时使用
  另一种的参数，所以迁移后的写入继续使用 600,000 次。
- 用户明确清除钱包数据后，如果两种密文都已不存在，之后创建的是新的本地钱包。

## 迁移与恢复

解锁成功后，迁移在空闲阶段重新验证密码，从持久化密文读取完整的 vault，重加密
仍为 5,000 次的字段，并验证新密文可读。只有 `booted` 的旧钱包只迁移该字段。
如果当前会话失效、其他操作改写了凭据或正在写入 vault，本次迁移会退出，之后解锁
时重试。纯缓存密钥解锁仍须通过密码验证才可迁移。

先写入并验证完整的 600,000 次 checkpoint，再替换主记录。两份记录均写入成功后
才发布内存状态和新缓存密钥。主记录仍可读时，下次启动优先加载它，旧记录会再次
安排迁移。如果主记录在替换中损坏，启动时可从已验证的 checkpoint 恢复。旧生物
识别缓存与新 vault 不匹配时，通过已保存的密码解锁并刷新缓存。

## 密文与读取兼容

600,000 次密文在原来的 `cipher`、`iv`、`salt` 之外增加：

```json
{
  "kdf": {
    "version": "20261022",
    "algorithm": "PBKDF2",
    "hash": "sha256",
    "iterations": 600000
  }
}
```

- 同时缺少 `kdf` 和 `keyMetadata` 的旧密文固定按 5,000 次读取；密码校验失败后
  不再尝试 600,000 次。高迭代密文必须携带元数据，不支持无元数据的高迭代测试密文。
- 有元数据时继续兼容版本化的 `kdf` 和旧 `keyMetadata`，按声明的参数读取。
- `decrypt` 和 `decryptWithDetail` 读取密文自身参数，不依赖实例写入策略。
- 参数仅接受 PBKDF2 的 5,000 或 600,000 次。损坏、未知或过大的参数直接报错，
  不回退到另一组参数重试。
- 600,000 次导出密钥也保存 `kdf`，缓存解密同时检查 salt 和派生参数，
  并继续跳过 PBKDF2。旧版不含元数据的导出密钥仍可用于旧密文。
- salt 编码、IV、摘要算法和 AES 模式保持原实现。

不包含本功能的旧 App 无法通过密码读取 600,000 次本地 vault。新旧参数共存解决的是
当前及后续版本中的升级与长期读取兼容。只有支持 600,000 次元数据的版本才能读取
迁移后的 vault。
云备份使用独立的普通 encryptor 默认策略，不会仅因本地新钱包使用 600,000 次而改写。

## 验证与性能边界

`encryptor.test.ts` 是单模块 unit 测试，在原生 AES 边界使用 Node crypto，覆盖固定
向量、新旧格式读取、新 keyring 的 600,000 次选择及既有密文参数继承。
`keyringVaultUpgrade.integration.test.ts` 组合真实 KeyringService、RNEncryptor、
ObservableStore 与持久化协调器，覆盖空闲调度、密码与生物识别解锁、并发写入、
迁移中断后的重试与 checkpoint 恢复。Node 测试将原生 AES 和 MMKV 替换为边界替身。

迁移的密钥派生在解锁后进行。迁移完成后的密码校验和密码解锁需要按密文声明的
600,000 次派生，有效的生物识别缓存继续跳过 PBKDF2。Android 的 600,000 次派生
优先使用 QuickCrypto 的异步实现，失败时使用原生 AES 模块提供的同一组派生参数。
两个实现均将保存的 salt 字符串按 UTF-8 输入，并向 AES 提供 32 字节密钥的十六进制表示。
设备验证需覆盖实际解锁耗时与进程中断后的 MMKV 恢复。
